JHB Curtain Cleaning is Johannesburg's premier on-site curtain cleaning service, founded by Stephen Dunlop — an industry veteran with 15+ years of hands-on experience who has personally served more than 5,000 clients across Gauteng. The business operates from 10 2nd Ave, Florida, Roodepoort, 1710 and offers a six-service portfolio covering curtain & blind cleaning, mattress sanitisation, upholstery & carpet cleaning, master guarding, fire proofing, and rug care. Service is delivered on-site at the customer's premises, eliminating the disruption of removing curtains for off-site treatment.

The website is a production-ready Next.js 16 application built on the App Router, comprising 19 routes: 1 homepage, 6 service landing pages, 6 sector landing pages, 6 area landing pages, and 3 API endpoints (/api/chat, /api/contact, /api/newsletter). A further sitemap.xml and robots.txt are auto-generated. All 18 landing pages are statically generated at build time via generateStaticParams, producing an ultra-fast, SEO-optimized site that scores well on Core Web Vitals.

The site is live at two URLs: https://curtaincleaning.space-z.ai/ (the Z.ai workspace preview/staging environment) and https://jhbcurtaincleaning.co.za (the production custom domain). The www subdomain issues a 308 redirect to the apex domain. A Vercel subdomain (jhb-curtain-cleaning.vercel.app) remains available as a backup URL. Both primary URLs point to the same Vercel deployment, ensuring parity between staging and production builds.

Deployment runs on Vercel (Hobby plan, region iad1 — Washington DC), with auto-deploys triggered on every push to the main branch of the GitHub repository otsmarketing01-debug/jhb. Build time is approximately 90 seconds end-to-end. The current production commit is 2808d8b. The codebase contains 92 TypeScript/TSX files totalling roughly 13,721 lines of code, including the central content data file (src/lib/site-data.ts) which alone is 1,175+ lines.

The technology stack is deliberately conservative and best-of-breed: Next.js 16 + TypeScript 5 + Tailwind CSS 4 + shadcn/ui (48 Radix-based components) + Framer Motion 12 + Prisma 6 + z-ai-web-dev-sdk. The build pipeline is managed by Bun as the package manager and script runner. State management is split between Zustand (client) and TanStack Query (server). The AI chatbot widget on every page is powered by the in-house z-ai-web-dev-sdk, hitting a serverless route that streams responses with thinking disabled for sub-second latency.

Static Generation Pattern

Each dynamic route (services, sectors, areas) implements both generateStaticParams (returning all 6 slugs at build time) and generateMetadata (producing per-page title, description, OpenGraph, canonical). The page component reads from the matching data constant (e.g., SERVICE_LANDING_DATA[slug]) and passes the content object to a client component (e.g., ServiceLandingClient) which renders the hero, two-column layout, sidebar, and JSON-LD scripts.

Section 05
Component Architecture

The component tree follows a strict three-layer separation: layout → page → section. The root layout injects fonts, JSON-LD schemas, and the global Toaster; pages compose section components; sections are pure presentational components that receive data via props from the central src/lib/site-data.ts constants. No section fetches its own data — all content flows down from a single source of truth, making bulk edits trivial.

The architecture deliberately duplicates the landing page client across three near-identical files (service-landing-client.tsx, sector-landing-client.tsx, area-landing-client.tsx) rather than abstracting them into a single generic component. While this introduces some repetition, it preserves the flexibility to diverge — sector pages, for example, render a keyStats block and decisionMaker section that services and areas do not. Each landing client receives a fully-typed content object from the parent page.tsx server component, which has looked up the slug in the corresponding data constant.

All floating widgets (WhatsAppButton, CookieConsent, AIChatbot) are mounted globally — the first two via the layout, the chatbot via the layout as well — so they appear on every route without per-page wiring. The Header uses an IntersectionObserver to detect the active section and applies a glass-morphism background once the user scrolls past 20px. The 4-step ContactSection is the most complex component at 844 lines, orchestrating React Hook Form state across four Framer Motion AnimatePresence stages.

Visual Hierarchy Rule

Emerald is the dominant color (≥60% of color mass: backgrounds of headers, footers, CTA bands). Bronze is the accent (≤25%: dividers, icon strokes, hover highlights, key emphasis). Ivory and white balance the layout (≥15%). This 60/25/15 ratio is enforced across every page for visual consistency.

Section 14
Contact Form System

The contact form (src/components/contact-section.tsx, 844 lines) is the most complex component in the codebase. It implements a 4-step wizard with React Hook Form for state management, Zod for schema validation, and Framer Motion's AnimatePresence for slide transitions between steps. Each step is gated — the user cannot advance until the current step passes its Zod schema.

Step 1 — Select Sector

6 radio options with icons (Hotels, Corporate, Healthcare, Education, Theatres, Residential). Required.

Step 2 — Select Area

Dropdown of 6 areas (JHB North, East, South, West, Central, Pretoria/Midrand). Required.

Step 3 — Your Details

Name, email, phone, property type (dropdown), window count (number), notes (textarea). All but notes required.

Step 4 — Confirmation

Review all entered details before submit. POPIA consent checkbox (required, must be literal true). Submit button.

  • React Hook Form + Zod — schema-driven validation; errors display inline beneath each field

Section 15
Landing Page Sidebar System

The LandingSidebar component (src/components/landing/landing-sidebar.tsx) is the conversion engine of every landing page. It renders 6 stacked cards in a sticky right-rail (1/3 width on desktop, full-width stacked on mobile). The sidebar receives all content via props from the parent landing client, which itself reads from the centralized landing data constant.

1. Assessment CTA Card

Gradient emerald header, checklist of what's included (3–4 items), prominent Book Free Assessment button. The primary conversion target on every landing page.

2. Guarantees Card

Shield icons + guarantee labels (5 items, sourced from GUARANTEES constant). Builds trust before the user reaches the contact form.

3. Get In Touch Card

Phone (click-to-call), email (mailto link), and stated response time (<2 business hours). Pulled from SITE_CONFIG.

4. Pricing Guide Card

4 tiers: Small / Medium / Large / Commercial. Each with a price range and brief description. Sets price expectations before form submission.

5. Related Services Card

Cross-links to other relevant services (2–3 items, excluding current page). Generated by getRelatedLinks() in src/lib/cross-links.ts.

6. Areas We Serve Card

6 area links (one per area). Always shows all 6 areas regardless of current page type, providing persistent cross-linking to area pages.

Props Interface

assessmentHeading, assessmentItems, guarantees, contact, pricingGuide, relatedServices, pageType. Sticky positioning via top-28 (112px) on desktop so the sidebar stays visible alongside the long-form main content column.

Section 16
Cross-Linking System

Internal linking is automated through a small utility (src/lib/cross-links.ts) and rendered via the RelatedLinks component. The function getRelatedLinks({ type, slug }) deterministically returns 6 cross-links for any landing page: 2 other services (excluding the current one if service-typed), 2 sectors, and 2 areas. This ensures every landing page passes link equity to a balanced mix of related pages.

Cross-Link Surface Area

Below-main RelatedLinks grid — 3-column responsive grid (6 items) placed before newsletter on all 18 landing pages
Sidebar "Related Services" card — 2–3 links to other services on every landing page
Sidebar "Areas We Serve" card — 6 area links on every landing page (always complete set)
Breadcrumbs — Home › Type › Current on all 18 landing pages
Footer 4 columns — Brand | Sectors (6 links) | Services (6 links) | Contact — appears on every page in the site

Internal Link Count

Each landing page contains approximately 40+ internal links (header dropdowns + breadcrumbs + sidebar cards + RelatedLinks grid + footer). With 18 landing pages, this generates 720+ internal links across the site, ensuring comprehensive crawl coverage and equitable PageRank distribution.
